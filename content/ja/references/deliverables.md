FDE の仕事は「動くもの」だけでなく、**顧客が自走できる状態**まで責任を持つこと。各フェーズで次の成果物を残すと、引き継ぎと成果の説明がしやすくなる。数値欄は案件ごとに実測値を入れ、推測値を書かない。

## 0. PoC 実施合意書（着手前）

PoC の失敗の大半は技術ではない。**「何が成功か」を合意していない**ことだ。着手前にこの 1 ページを埋めて、顧客と署名（またはメール合意）を取る。FDE 案件の必須スキル「要件と成果指標への落とし込み」の実体がこれである。

### テンプレート（記入例つき）

```markdown
# PoC 実施合意書（ドラフト）

### 1. 対象プロセス（1 つだけ）
入金消し込み（銀行明細と請求書の照合）

### 2. 期間
2026-10-01 〜 2026-10-31（4 週間）。週次定例 30 分（進捗と判定）。

### 3. 評価指標と合格閾値
- 明細ペアの抽出再現率 85% 以上（正解 100 件と照合）
- 差異抽出の誤検知率 10% 以下
- 判定方法: 顧客提供の正解データに対し、双方立会いのうえ計測

### 4. 顧客提供データ
- 銀行明細 CSV 3 か月分（仮名化済み、形式: 指定スキーマ）
- 請求書データ 200 件（PDF 可、個人情報マスク済み）
- 提供期限: 着手前まで。加工可否: 集計・抽出可、外部提供不可

### 5. 秘密保持
- 顧客データは顧客指定テナント（AWS アカウント）内でのみ処理
- 第三者 AI サービス利用時は契約プラン（学習利用なし）を事務処理規程に沿って確認
- データ持ち出し・複製は合意範囲内のみ

### 6. 成果物（検収基準）
- PoC 報告書（構成、結果、指標実測、本番化コスト見積もり）
- 動作するプロトタイプ（顧客テナント内またはデモ環境）
- 本番化に向けた課題リスト

### 7. 不合格時の取り扱い
- 閾値未達の場合: 追加検証 2 週間を 1 回まで実施（追加費用なし）
- それでも未達の場合: 本契約は締結せず、成果物とデータは返却・削除する
```

### 各フィールドで揉めるポイント（先に答えを用意する）

| フィールド | 典型的な論争 | 実務的な解 |
|---|---|---|
| 評価指標 | 「便利なら OK」で終わらせられる | 抽出再現率・誤検知率など**計測可能な式**に。判定方法も書く |
| 合格閾値 | 高すぎて絶対届かない / 低すぎて無意味 | 手作業の現状精度を測り、その**8〜9 割**を合格線に置く |
| 顧客提供データ | 「後で渡します」が永遠に来ない | 形式・件数・**提供期限**を合意書に。遅延は期間の自動延長条項で守る |
| 秘密保持 | 「外部 AI に入れていいの?」 | テナント内処理・契約プランの学習利用なし・規程確認を 3 点セットで明記 |
| 不合格時 | 追加作業が無限に続く | 追加検証の回数・期間・費用を最初に固定する |

### 検収の勘所

- 合格判定は**双方立会い**で実施し、結果を数値で議事録に残す
- 「顧客の満足」ではなく合意書の閾値で判定する（満足度は本番化の議論で扱う）
- 本番化コスト見積もり（[コスト見積もり](/guide/cost-and-roi)）を成果物に含めると、次の契約が自然に決まる

成果指標の 3 層（業務・品質・ガードレール）の決め方は [要件化と成果指標](/guide/requirements-and-kpi) を参照。

## 1. 業務分析シート（要件定義）

| 項目 | 記入内容 |
| --- | --- |
| 対象業務 | 業務名・担当部署・頻度 |
| 現状の手順 | ステップごとの作業内容と所要時間（実測） |
| AI に任せる作業 | 下書き・分類・要約など |
| 人が残す判断 | 承認・確定・例外対応 |
| 入力データ | 所在・形式・機密区分 |
| 成果指標 | 何がどれだけ変われば成功か（[PoC 合意書](/references/deliverables)と連動） |

## 2. 評価計画（設計〜テスト）

- ゴールデンデータの件数・作成者・作成日
- 評価観点（正確性・網羅性・形式・トーン）と合格閾値
- 回帰評価の実行タイミング（プロンプト / モデル変更時）
- 詳細は[評価パターン](/patterns/evaluation)

## 3. リスク登録簿

| リスク | 影響 | 対策 | 担当 |
| --- | --- | --- | --- |
| 誤った出力が顧客に届く | | 承認フロー（[Human-in-the-loop](/patterns/human-in-the-loop)） | |
| 機密情報の外部送信 | | 区分表と匿名化（[機密入力](/patterns/confidential-inputs)） | |
| プロンプトインジェクション | | 入力の分離・権限最小化 | |
| モデル更新による挙動変化 | | 回帰評価 | |

LLM アプリ特有のリスクの網羅には [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llm-top-10/) が参照しやすい。

## 4. 運用移管書（導入・保守）

- 運用担当者と問い合わせ窓口
- プロンプト・参照文書の更新手順と承認者
- 監視項目（利用量・エラー率・修正率・コスト）
- 停止・ロールバック手順
- 次の改善候補（バックログ）

## 5. 成果報告（クロージング）

- 合意した成果指標の導入前 / 後の実測値と測定方法
- 想定どおりにいかなかった点と理由
- 横展開できる業務の候補

## チェックリスト

- [ ] 全成果物に作成日・作成者・顧客側承認者が記載されている
- [ ] 数値はすべて実測値で、測定方法が書かれている
- [ ] 顧客側の担当者だけで運用を継続できる
