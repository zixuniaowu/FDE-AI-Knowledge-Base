## 概要

「1 つの巨大プロンプト」は途中で指示が破綻しやすい。**タスクを段階に分割し、各段階の出力を次の入力にする**パターン。各段階で品質チェックと人間の介入点を作れる。

## 仕組み

```mermaid
flowchart LR
    A["1 調査・収集"] --> V1{{"検証<br/>（構造化出力）"}}
    V1 -->|合格| B["2 構成案"]
    V1 -.->|不合格・差し戻し| A
    B --> V2{{"検証"}}
    V2 -->|合格| C["3 本文ドラフト"]
    V2 -.->|不合格・差し戻し| B
    C --> V3{{"検証"}}
    V3 -->|合格| D["4 校正・トーン調整"]
    V3 -.->|不合格・差し戻し| C
    D --> H(("人間の検収"))
```

## 適している場面

- 長文書の作成（レポート・提案書・手順書）
- 調査 → まとめ → 提案のような多段の業務
- 途中の品質が最終品質を決めるタスク

## 各領域での応用

- 教育: [授業教材](../domains/education/use-cases/lesson-material-draft.md)（目標 → 構成 → 本文 → 演習問題）
- マーケティング: [コンテンツ制作](../domains/marketing/use-cases/content-drafting.md)の段階分割
- 製造: 手順書（ヒアリング整理 → ドラフト → 安全確認 → 統一フォーマット化）

## 落とし穴

- 段階をまたいで文脈が落ちる: 各段階の出力に「次の段階に必要な情報」を持たせる
- 分割しすぎで遅い・コスト高い: 3〜5 段階が目安。逆効果なら統合する
- エラーの伝播: 各段階に検証（[構造化出力](./structured-output.md)）を入れ、不合格は次へ進めない

## 使うか・使わないか（判断表）

| 状況 | 判断 | 代わりの選択肢 |
|---|---|---|
| 1 回のプロンプトで指示が多すぎて品質が落ちる | 使う | — |
| 中間結果を人や検証にかけたい | 使う | — |
| 速度・コストが最優先 | 使わない（呼び出し回数が増える） | 1 回のプロンプト + [Structured Output](/patterns/structured-output) |
| 手順が入力によって変わる | 分岐付きのチェーン、または | [Agent](/patterns/agent) |

## 導入の手順

1. 業務の手順を、人がやるときの単位で分解する
2. 各ステップの入力・出力の形式を決める（構造化出力が望ましい）
3. ステップ間に検証（ルールチェック）を入れ、失敗したら止める
4. ステップごとに評価し、品質のボトルネックになっているステップを特定する

## 例示: 議事録からタスク管理への登録（架空のケース）

> 手法の説明用の**架空の例**です。特定の企業の事例ではありません。

①文字起こしを要約 → ②決定事項とアクションを JSON 抽出 → ③担当者名を社員マスタと照合（ルール） → ④登録前に会議主催者が確認。②と③を分けたことで、担当者名の誤りがどこで起きたかを特定できるようになった

## 導入チェックリスト

- [ ] 各段階の入出力をスキーマで定義した
- [ ] 段階ごとに検証を入れ、不合格は次へ進めない
- [ ] 段階別の所要時間とコストを計測している
- [ ] どの段階で品質が落ちるかをログから追える
