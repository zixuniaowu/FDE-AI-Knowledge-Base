## 概要

単発の Q&A ではなく、**目標とツールを渡して AI に計画・実行・確認のループを回させる**パターン。「資料を集めて比較表を作る」「このリポジトリのバグを直して PR を出す」のような複数ステップのタスクを対象にします。

## 仕組み

```mermaid
stateDiagram-v2
    [*] --> 計画: 目標とツールを渡す
    計画 --> ツール実行: 1 ステップを選択<br/>（検索 / コード実行 / ファイル操作）
    ツール実行 --> 観察: 結果と行動ログを記録
    観察 --> 計画: 結果を踏まえて再計画
    観察 --> 成果物の提示: 目標達成と判定
    計画 --> 停止: 上限到達<br/>（10 ステップ / $2）
    ツール実行 --> 停止: 書き込み系は人間承認が必須
    停止 --> 計画: 人間が確認して再開
    成果物の提示 --> [*]
```

## 適している場面

- 手順が事前に完全には決められない、探索的なタスク（調査・デバッグ）
- 複数ツールをまたぐ作業（検索 → 集計 → レポート化）
- 反復のたびに結果を見て次を変える必要がある作業

## 各領域での応用

| 領域 | 応用例 |
|---|---|
| ソフトウェア開発 | バグ再現 → 修正 → テスト → PR 作成の自動化 |
| マーケティング | 競合調査 → 整理 → 比較レポート作成 |
| 製造 | 不具合データの横断集計と傾向レポート |
| 法務 | 関連条文・判例の横断調査と一覧化 |

## 落とし穴

- **暴走と無限ループ**: 実行回数・コストの上限を必ず設定する
- 誤った結果を累積する: 中間成果を人間がチェックポイントで確認する（[Human-in-the-loop](./human-in-the-loop.md)と組み合わせる）
- 権限が大きすぎる: ツールごとに最小権限を与え、破壊的操作は人間の承認を必須にする
- 「何をしたか分からない」: 行動ログの記録を必須にする

## 上限・ツール定義・ログの具体例

| 設定 | 推奨初期値 | 理由 |
|---|---|---|
| 最大ステップ数 | 10 ステップ | 無限ループの防止。足りなければ人間が継続を判断 |
| コスト上限 | $2/タスク | 暴走時の損害を固定額にする |
| ツール権限 | 読み取り系のみ / 書き込みは承認必須 | 破壊的操作（削除・送信）は人間の承認を必須化 |

ツール定義のスキーマ例:

```json
{ "name": "search_docs", "input_schema": { "type": "object",
  "required": ["query"], "properties": { "query": { "type": "string" }, "limit": { "type": "integer", "maximum": 20 } } } }
```

行動ログの形式（1 ステップ 1 行・JSON）:

```json
{ "step": 3, "tool": "search_docs", "input": {"query": "返品規定"}, "result_summary": "3 件ヒット", "tokens": 1420, "elapsed_ms": 830 }
```

このログがないエージェントは、失敗したときに何が起きたか説明できない。

## 正常ログ vs 暴走ログの見分け

✅ **正常**: 各ステップのツールが変わり、tokens が一定範囲（例: 1 ステップ 500〜2000）で、入力と出力が課題に関連している

❌ **暴走**: 同一ツールを同一引数で 3 回以上繰り返す / tokens が急増 / 読み取り専用のはずが書き込み系ツールを呼ぶ。→ 上限（10 ステップ / $2）で止まり、ログを人間が確認してから再開する

## 使うか・使わないか（判断表）

| 状況 | 判断 | 代わりの選択肢 |
|---|---|---|
| 手順が固定で分岐が少ない | 使わない | ワークフロー（[Prompt Chaining](/patterns/prompt-chaining)） |
| 必要な手順が入力によって大きく変わる | 使う | — |
| 書き込み・送信・削除を伴う | 使うなら承認必須 | [Human-in-the-loop](/patterns/human-in-the-loop) |
| 1 回の誤りの損害が大きい | 使わない／読み取り専用に限定 | — |

## 導入の手順

1. まずワークフロー（固定手順）で作れないか検討する
2. ツールを読み取り系と書き込み系に分け、書き込み系は承認制にする
3. ステップ数・コスト・時間の上限を設定する
4. 全ステップのログ（思考・ツール呼び出し・結果）を保存する
5. 評価セットで成功率と暴走（上限到達）率を測る
6. 限定した利用者・業務から始め、ログを週次でレビューする

## 例示: 社内 IT ヘルプデスクの一次対応（架空のケース）

> 手法の説明用の**架空の例**です。特定の企業の事例ではありません。

問い合わせ内容に応じて、FAQ 検索・アカウント状態の照会（読み取り）・チケット起票（書き込み・承認制）を使い分ける。上限は 8 ステップ。ログのレビューで「同じ FAQ 検索を繰り返す」暴走が見つかり、直前と同じ検索を禁止する制約を加えた

## 導入チェックリスト

- [ ] ツールごとに権限（読み取り / 書き込み）を分け、書き込み系は承認を挟む
- [ ] ステップ数・実行時間・費用の上限を設定した
- [ ] 全ステップのツール呼び出しと引数をログに残す
- [ ] 失敗時に安全に止まり、人に引き継ぐ経路がある
- [ ] 外部入力（メール・Web）に埋め込まれた指示を実行しない対策を入れた
